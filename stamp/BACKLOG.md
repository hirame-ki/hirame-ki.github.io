검토는 끝났지만 구현하지 않았던 3건. 나중에 판단하기 위한 기록이다.
행 번호는 `efd8795` 시점의 `index.html` 기준이라 지금 파일과는 어긋난다.

> **2026-08-20 현재 — 3건 중 2건을 구현했다.**

> |---|---|
> | 1. 원주 배치 | **구현 완료** |

## 먼저 알아둘 것 — 1번과 2번은 같은 벽에 막혀 있다

지금 구조는 **글자 덩어리를 하나만** 다룰 수 있다.

```js
// 885행
const all = chars.concat([...st.suffix]);   // 이름 + 접미사를 한 배열로 합친다
```

이 배열 하나가 `layoutCells`(818행) → `buildCells`(843행) → `render`의 글자 루프로 흘러가고,
전부 **같은 격자, 같은 크기, 같은 회전**을 받는다.

그런데 원주 배치도 날짜 삽입도 **성격이 다른 두 번째 덩어리**를 요구한다.
바깥 테두리를 도는 기관명과 가운데 직위, 또는 본문과 아래쪽 날짜처럼.

> **둘 중 하나라도 하기로 하면, 먼저 "글자 덩어리 여러 개"를 표현할 수 있게 상태와 렌더를 고쳐야 한다.**
> 이 리팩터링을 한 번 해두면 두 기능 모두 그 위에 얹힌다. 따로 하면 두 번 고생한다.

대략 이런 모양이 된다.

```js
S.blocks = [
  { text:'○○고등학교', role:'ring'   },   // 테두리를 도는 글자
  { text:'교장',        role:'center' },   // 가운데 격자
]
```

## 1. 원주 배치

테두리를 따라 글자가 도는 형태. 관인에서 가장 흔한 모양이라 "관공서 도장답다"는
인상에 기여하는 바가 크다. 3건 중 **효과는 가장 크고 품도 가장 많이 든다.**

### 손대야 하는 곳

| 위치 | 할 일 |
|---|---|
| 818행 `layoutCells` | `ring` 모드 추가. 지금은 격자(cols/counts)만 낸다 |
| 843행 `buildCells` | 칸마다 중심좌표 + **회전각**을 함께 내야 한다. 지금은 `{cx, cy, w, h}`뿐 |
| 882행 `render` 글자 루프 | 글자마다 `ctx.rotate()`를 걸어 접선 방향으로 세운다 |

### 걸림돌

- **테두리가 정원이 아니다.** `shapeRadii`(784행)와 `shapeExp`(781행)가 만드는 건
  초타원이라 타원·둥근사각에서도 글자가 고르게 배치되려면 **호 길이 기준으로
  나눠야 한다.** 각도를 균등 분할하면 타원의 옆구리에서 글자가 뭉친다.
  → 곡선을 잘게 쪼개 누적 길이표를 만들고 거기서 역으로 위치를 찾는 방식이 필요하다.
  `outlinePath`(796행)가 이미 곡선을 N등분해 그리므로 그 코드를 재사용할 여지가 있다.
- **`stretch`와 `글자 크기`의 의미가 흐려진다.** 칸이 사각형이 아니게 되므로
  "칸에 꽉 채우기"를 어떻게 해석할지 다시 정해야 한다.
- **`전통 순서`가 방향 문제로 바뀐다.** 시계/반시계, 시작 각도를 어디로 둘지.
- 사각 도장에서는 모서리를 어떻게 처리할지 — 대개 원형·타원에서만 허용한다.

### 판단 포인트

**"글자 덩어리 여러 개" 리팩터링까지 포함하면 이번 작업들 중 가장 크다.**
반대로 이것 하나로 도구의 인상이 크게 달라지므로, 다음에 큰 덩어리를 한 번
잡을 여유가 생기면 1순위로 둘 만하다.

### 구현 완료 (2026-08-20)

**가장 크다고 본 걸림돌 — 상태 구조 — 은 실제로는 없었다.**

`S.blocks` 를 새로 세울 필요가 없었다. `text` 와 `suffix` 가 **이미** 성격이 다른
두 덩어리였기 때문이다. 이름을 테두리로, 접미사를 가운데로 보내는 것만으로
관인의 모양이 나온다. 상태는 한 글자도 늘지 않았다.

대신 **글자를 그리는 루프를 `drawGlyphs` 로 떼어 냈다.** 칸 목록만 받고 칸을
어떻게 만들었는지는 따지지 않으므로, 격자 배치와 원주 배치가 이 함수를 함께 쓴다.
"덩어리 여러 개"에 필요했던 건 상태 구조가 아니라 이 분리 하나였다.

| 새로 생긴 것 | 하는 일 |
|---|---|
| `arcTable` | 곡선을 1440등분해 누적 길이표를 만든다 |
| `lengthAt` / `angleAt` | 각도 ↔ 누적 길이를 서로 바꾼다 (이분 탐색) |
| `buildRingCells` | 테두리를 도는 칸. `{cx, cy, w, h, rot}` 을 낸다 |
| `drawGlyphs` | 칸 목록에 글자를 앉힌다. `cell.rot` 이 있으면 회전을 건다 |

**걸림돌별 결말**

- **호 길이 계산** — 예상대로 필요했다. 타원 8자에서 각도 균등 분할은 간격 편차가
  **14.9%** 인데 호 길이 기준은 **0%** 다. 원·타원·둥근사각·사각 네 도형 모두
  독립 적분으로 편차 0.00% 를 확인했다.
- **`stretch` 의 의미** — 흐려지지 않았다. 칸에 `w`/`h` 가 있으므로 기존 규칙이
  그대로 성립한다. 다만 칸 너비를 호 길이 그대로 두면 글자가 옆으로 늘어나
  **띠 두께로 한 번 눌러야** 했다. 그 기준은 띠의 **안쪽 가장자리**다 — 곡선에서는
  바깥이 벌어지는 만큼 안쪽이 좁아져, 12자가 넘으면 안쪽 모서리끼리 부딪힌다.
- **`전통 순서`** — 방향으로 재해석했다. 켜면 위에서 왼쪽으로 돈다(각도 감소).
  시작 각도는 첫 글자를 위쪽 한가운데(-90°)에 두는 것으로 고정했다.
- **사각 모서리** — 막지 않았다. 깨지지는 않으나 모서리에서 글자가 비스듬히
  서서 어색하다. **원형·타원·둥근사각을 권한다.**

**눈으로 확인한 것** — 3/6/8/12/16자, 네 도형, 음각, 이중 테두리, 접미사
없음/`인`/`之印`, 방향 반대, 프리셋 적용, 설정 저장·복원까지 브라우저에서 그려
봤다. 콘솔 오류 없음.

**튜닝 값** — 띠 두께는 안쪽 반지름의 `0.42`. 가운데 글자는 그냥 두면 띠 글자의
**2.49배**가 되어 도장을 잡아먹으므로 `1.35배`에서 끊는다. 둘 다 눈으로 비교해
고른 값이다.

> 이 두 값은 **아래 「다시 고침」에서 바뀌었다.** 가운데에 진짜 글자가 들어가고
> 안쪽 원이 생기면서 비율을 다시 잡아야 했다. 지금 값은 띠 `20~55%`(슬라이더,
> 기본 34)이고 가운데 상한은 없앴다.

### 다시 고침 — 가운데 글자 (2026-08-20)

위에서 "남은 것"으로 미뤄 둔 자유 문구를 바로 넣었다. **접미사 한 글자만으로는
관인처럼 보이지 않았기 때문이다.** 실제 관인의 가운데에는 `교장`, `대표이사`
같은 직위가 들어간다.

- `S.mid` 를 두고 **가운데 글자 입력칸**을 따로 냈다. 원주일 때만 나타난다
- 위 칸 이름이 `도장에 넣을 글자` → `테두리 글자` 로 바뀐다. 같은 칸이 배치에
  따라 다른 자리를 뜻하므로 이름도 따라가야 한다
- **안쪽 원**을 그린다. 이 선이 없으면 두 덩어리가 각자의 자리를 가진 것으로
  보이지 않고 글자가 흩어져 보인다

**놓쳤다가 고친 것** — 선을 띠 글자의 안쪽 끝에 그대로 그었더니 **선이 글자를
관통했다.** 띠 글자가 그 경계까지 꽉 차기 때문이다. 한 뼘 더 안쪽(`× 1.16`)으로
물렸다. 반지름 순서를 `띠 글자 안쪽 > 선 > 가운데 글자 바깥` 으로 확인했다
(700px 기준 186.7 > 171.3 > 154).

가운데가 비면 선을 긋지 않고, 대신 띠를 `0.34` → `0.46` 으로 넓혀 글자를 키운다.

**두 원의 간격을 슬라이더로 뺐다** — 띠 두께 하나가 곧 바깥 원과 안쪽 원의
간격이다. 키우면 안쪽 원이 작아지고 테두리 글자가 커진다. 어느 쪽이 맞는지는
글자 수와 취향에 달렸으므로 고정할 값이 아니었다. `20~55%`, 기본 `34%`.
전 구간에서 위의 반지름 순서가 깨지지 않는 것을 확인했다.

**이중 테두리는 원주에서 아예 그리지 않는다** — 안쪽 원이 이미 두 번째 선이라,
쌍선까지 켜면 바깥 두 줄 + 안쪽 한 줄로 선이 셋이 된다.

> **프리셋만 고쳐서는 안 됐다.** 처음에 `기관장 직인` 의 `dbl` 만 껐는데,
> **설정이 브라우저에 저장되므로 이미 켜 둔 사람에게는 아무 변화가 없었다.**
> 프리셋을 다시 누르지 않는 한 그대로다. 기본값을 바꾸는 것과 이미 저장된
> 상태를 바로잡는 것은 다른 일이라는 걸 놓쳤다.

그래서 `dblOn` 조건에 `layout!=='ring'` 을 넣어 **상태와 무관하게** 그리지 않게
했다. 체크박스는 원주일 때 잠기고, 다른 배치로 돌아가면 풀린다.

이 김에 그리는 쪽이 `st.dbl` 을 직접 보던 것을 `dblOn` 으로 바꿨다. 자리
계산(`dblTotal`)은 `dblOn` 을 쓰는데 그리기는 `st.dbl` 을 봐서, 두 조건이
갈리는 순간 어긋나는 구조였다.

**글씨체 추가 시 주의** — `fontIdx` 는 `FONTS` 배열의 번호가 그대로 저장된다.
구기를 중간에 끼웠다가 이미 저장된 설정이 다른 글씨체를 가리키게 되는 것을
발견해 맨 뒤로 옮겼다. **새 글씨체는 반드시 배열 끝에 붙일 것.** 목록에서의
자리는 `group` 이 정하므로 뒤에 붙여도 원하는 칸에 들어간다.

**남은 것** — 프리셋은 `mid` 를 건드리지 않는다. `text` 와 같은 자유 입력이라
프리셋이 덮어쓰면 사용자가 친 글이 날아간다. 그래서 `기관장 직인` 을 눌러도
가운데는 접미사 한 글자뿐이다. 프리셋에 예시 문구를 넣을지는 판단이 필요하다.

**한글 전서체는 넣지 않았다** — 도장 하면 떠오르는 각지고 꼬인 글씨는
`HJ한전서A/B` 다. 저작권자가 Next Vision(한진)으로 보이나 **사용 범위가 공개된
적이 없어** 유·무료조차 확인되지 않는다. 게다가 **2011년 2월 행정안전부가
「사무관리규정 시행규칙」을 고쳐 관인 서체를 '한글 전서체'에서 '한글'로 바꿨다**
— 읽기 어렵고 권위주의적이라는 이유로 63년 만에 빠졌다. 가장 가까운 각진 느낌
으로 Google Fonts 의 구기(Gugi)를 넣어 뒀으나 전서체는 아니다.

### 세 번째 고침 — 영문이 섞이면 무너졌다 (2026-08-20)

테두리 글자에 `인스타 @hirame.ki` 를 넣어 견본을 뽑고 나서야 드러났다.
**마침표가 커다란 점(●)이 되고** `i`·`k` 는 크고 `m`·`a`·`r` 은 작아 크기가
제멋대로였다.

원인은 원주와 무관했다. `drawGlyphs` 가 글자마다 **제 잉크를 칸에 꽉 채우도록**
키우는데, 이건 잉크가 정사각형에 고르게 차는 **한글·한자를 전제한 계산**이다.
영문·숫자·부호는 글자마다 잉크 범위가 딴판이라, 잉크가 거의 없는 마침표가
칸을 채우려고 부풀어 버린다.

`FULLWIDTH` 정규식으로 갈랐다.

| 무리 | 크기 정하는 법 |
|---|---|
| 한글·한자·전각 부호 | 전과 같이 제 잉크를 칸에 꽉 채운다 |
| 영문·숫자·부호 | 기준 글자('가')가 받았을 배율을 그대로 쓴다 |

세로 위치도 갈라야 했다. 영문은 기준 글자의 밑선에 맞춘다 — 제각기 가운데를
맞추면 `a` 와 `h` 의 밑이 어긋난다.

**회귀 검사** — 견본 60장을 다시 뽑아 md5 를 파일별로 대조했다. 한글·한자만
쓰는 36장은 **바이트까지 그대로**, 영문이 섞인 원주 24장만 바뀌었다.
기존 도장은 조금도 달라지지 않는다.

> **배운 것** — 이 코드는 "글자 하나 = 정사각형 한 칸"을 당연하게 깔고 있었다.
> 원주를 넣으면서 그 전제가 흔들린 게 아니라, **원주가 그 전제를 처음으로
> 시험했을 뿐**이다. 앞으로 숫자·영문이 들어가는 기능(날짜 삽입!)을 붙일 때
> 같은 자리를 다시 보게 된다.

## 2. 날짜 자동 삽입

`검토필` 아래에 `2026.08.16` 같은 날짜를 넣는 형태. 확인 도장 용도.

### 손대야 하는 곳

- 708행 `S`에 `date` 관련 상태 추가 (켜기/끄기, 형식)
- 위의 "글자 덩어리 여러 개" 구조 — 날짜는 본문보다 작고 아래쪽에 따로 놓인다
- 조작부에 형식 선택 (`2026.08.16` / `26.8.16` / `2026년 8월 16일`)

### 걸림돌

- 구조 문제는 1번과 동일하다. 단독으로 하면 리팩터링 비용을 혼자 다 낸다.
- **찍는 시점의 날짜인지, 고정 날짜인지** 정해야 한다. 자동이면 어제 만든
  파일을 오늘 다시 열었을 때 날짜가 바뀐다. 저장된 설정과 충돌한다.

### 지금은 어떤가 (2026-08-20)

## 3. 관인 규격 프리셋

기관 관인의 법정 크기에 맞춘 프리셋. 3건 중 **코드는 가장 간단하지만
사실 확인이 안 돼 막혀 있다.**

> **2026-08-20 진행** — 근거 법령은 특정했다. 별표 수치는 여전히 못 구해
> "법정 규격 프리셋"은 그대로 막혀 있다.
>
> 대신 **물리 크기 문제를 먼저 풀었다.** 아래 「확인된 뒤에도 남는 문제」에
> 적어 둔 dpi·pHYs 이야기가 사실은 규격 수치와 무관하게 혼자 풀 수 있는
> 문제였다. 크기를 mm 로 고르고 `pHYs` 를 심어 저장하도록 바꿨으므로,
> 나중에 별표 수치를 구하면 **선택지에 값 몇 개를 더하는 것으로 끝난다.**

### 확인된 것

- 근거는 「행정업무의 운영 및 혁신에 관한 규정」(대통령령) **제35조(규격)**.
  조문은 "관인의 모양은 **별표의 규격을 초과하지 아니하는 범위에서** 행정기관의
  장이 정한다"이다.
- 즉 **규격은 상한선이지 고정 치수가 아니다.** 프리셋을 만들더라도 "이 크기여야
  합니다"가 아니라 "이 크기를 넘지 않습니다"로 써야 맞다. 이 차이 때문에
  프리셋의 쓸모 자체가 처음 생각보다 작을 수 있다.
- 관인은 청인(합의제 기관의 기관 명의)과 직인(기관장 직위 명의)으로 나뉜다
  (제33조).

### 아직 막힌 지점

**별표 「관인의 규격」의 실제 수치를 구하지 못했다.**
법제처·국가법령정보센터·위키문헌·LBOX·U-LEX·나무위키를 확인했으나 어디든
목차에 `[별표] 관인의 규격(제35조 관련)`만 있고 본문 표는 이미지·HWP 첨부라
읽히지 않는다. 근거 없이 수치를 박으면 공공기관 사용자에게 잘못된 정보를
주게 되므로 프리셋은 손대지 않았다.

남은 확인 거리:

- 별표 본문 — HWP 첨부를 직접 내려받거나 인쇄물로 확인하는 수밖에 없어 보인다
- 종류별로 다른지 (청인/직인, 기관 등급별)
- 지름 기준인지 한 변 기준인지

### ~~확인된 뒤에도 남는 문제~~ — 해결됨 (2026-08-20)

~~**이 도구에는 물리 크기 개념이 아예 없다.** 내보내기는 px 단위뿐이다.~~

당시 "규격 수치를 구한 다음에나 손댈 문제"로 묶어 두었으나, **잘못 묶었다.**
물리 크기 문제는 별표와 아무 상관이 없어 혼자 풀 수 있었다. 아래 절충안 항목에
푼 내용을 적었다.

- mm → px 환산의 dpi 가정 → **600dpi 로 정했다**
- 캔버스 `toBlob` 이 pHYs 를 안 넣는 문제 → **저장 직전에 직접 심는다**
- "제대로 하려면 PNG 바이트를 직접 만져야 한다" → **그렇게 했다.** 겁냈던 것에
  비해 40줄 남짓이었다

### 판단 포인트

**규격 수치만 확보되면 프리셋 자체는 반나절 거리다.** 물리 크기 문제를 이미
풀어 두었으므로, 이제는 정말로 **선택지에 값을 더하는 일**만 남는다.

가벼운 절충안: 규격 프리셋 대신 **내보내기에 "인쇄 시 실제 크기" 안내 한 줄**만
붙이는 것. `1024px = 300dpi에서 약 87mm` 식으로. 이건 지금도 바로 할 수 있다.

**→ 절충안은 버리고 제대로 풀었다.** 안내 문구를 한 번 써 보고서야
그게 답이 아니라는 게 드러났다.

> `300dpi로 인쇄하면 약 87mm입니다. 3cm로 줄여 넣으면 867dpi가 됩니다.`

**읽는 사람이 dpi 를 알아야 이해되는 문장이었다.** 게다가 사용자는 크기 선택을
보고 "고른 크기로 저장된다"고 읽는다 — 실제로는 그렇지 않은데. 설명으로
메울 문제가 아니라 **동작을 기대에 맞추는 게 맞았다.**

그래서 `pHYs` 를 직접 심는 쪽으로 갔다.

- 크기 선택을 px → **mm** 로 바꿨다 (`12 / 15 / 18 / 21 / 24 / 30mm`, 기본 15mm)
- 픽셀 수는 1200dpi 로 환산해 정한다 (15mm → 709px). 도장이 작아 600dpi 로는
  12mm 가 283px 밖에 안 됐다
- 저장 직전 `withPhysicalSize` 가 IHDR 바로 뒤에 pHYs 청크를 끼워 넣는다.
  CRC32 표를 직접 만들어 쓴다 (21바이트: 길이4 + 타입4 + 데이터9 + CRC4)
- PNG 서명이나 IHDR 이 예상과 다르면 원본을 그대로 돌려준다. 크기 정보가
  빠질 뿐 그림은 멀쩡하다
- 안내 줄은 `한글·워드에 넣으면 30mm 크기로 들어옵니다.` 한 줄로 끝난다

**한글에서 고른 크기 그대로 들어오는 것을 확인했다.** pHYs 를 읽는다.

### 선택지를 두 번 고쳐 잡았다

처음 내놓은 `20 / 25 / 30 / 40mm` 는 **실제 도장보다 한참 컸다.** 화면에서
숫자만 보면 몰랐는데, 종이에 앉히고 보니 드러났다.

도장은 **푼(分)** 단위로 판다. **1푼 = 3mm** 라서 시중 규격이 12/15/18/21/24/30mm
로 떨어진다. 도장집에서 쓰는 말과 어긋나지 않게 mm 와 푼을 같이 적었다.

| 크기 | 푼 | 흔한 쓰임 |
|---|---|---|
| 12mm | 4푼 | 막도장 |
| 15mm | 5푼 | 개인 도장 — 기본값 |
| 18mm | 6푼 | 개인·법인 겸용 |
| 21mm | 7푼 | 사용인감 |
| 24mm | 8푼 | 직인 |
| 30mm | 10푼 | 큰 직인 |

**30mm 를 위쪽 끝으로 삼은 근거** — 개인 인감은 「인감증명법」상 가로·세로
**7mm 이상 30mm 이내**여야 한다. 처음에 넣었던 40mm 는 인감으로 등록조차
안 되는 크기였다.

**용어** — `손도장` 은 보통 지장(손가락 지문)을 뜻하므로 UI 에는 **막도장** 을 썼다.

쓰임 표기는 여전히 **흔히 쓰는 크기이지 법정 규격이 아니다.** 별표 수치를 구하면
선택지에 값을 더하는 것으로 끝나므로, 이 작업은 프리셋 본편의 **토대이기도 하다.**
